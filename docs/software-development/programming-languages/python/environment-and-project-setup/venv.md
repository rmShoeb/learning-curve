## How Python Locates Modules

- When executing an import statement like `import requests`, Python searches for the requested module in the ordered list of directory paths stored in `sys.path`.
- During interpreter startup, Python constructs `sys.path` dynamically in a specific order.
- **The Current Working Directory:** The directory containing the script used to invoke the Python interpreter (or the current interactive working directory).
- **`PYTHONPATH` Directory List:** Any directory paths explicitly set in the shell's `PYTHONPATH` environment variable.
- **Standard Library Directories:** The location of Python's core standard library compiled modules and source files (e.g., `/usr/lib/python3.11` or `C:\Python311\Lib`).
- **Site-Packages Directories:** Third-party package locations added by Python’s initialization standard module, `site.py`.

### The Role of `site.py` and Site Packages
- The site module is imported automatically during interpreter initialization (unless disabled via the `-S` command-line flag).
- Its primary responsibility is to find third-party installed packages and append their directories to `sys.path`.
- Site-Packages Directory:
	- On UNIX-like systems, this is typically located at `<prefix>/lib/pythonX.Y/site-packages`.
	- On Windows, it is located at `<prefix>\Lib\site-packages`.
- Path Configuration (`.pth`) Files:
	- During processing, `site.py` searches the site-packages directory for files ending with the `.pth` extension.
	- Each line inside a `.pth` file specifying a directory path is automatically validated and added to `sys.path`.
	- This enables tools like `pip install -e .` (editable installs) to expose package source code without physically copying files into `site-packages`.

## Anatomical Structure of a Virtual Environment
- A Python virtual environment is not a virtual machine or container.
- It is a lightweight, isolated directory structure containing a specific Python executable binary, supporting configuration files, and an independent `site-packages` directory.
- When created using `python3 -m venv .venv`, the directory layout structured on disk looks like this:
	```
	.venv/
	├── bin/ (or Scripts/ on Windows)
	│   ├── activate
	│   ├── activate.csh
	│   ├── activate.fish
	│   ├── pip
	│   ├── python -> /usr/bin/python3 (symlink)
	│   └── python3 -> python (symlink)
	├── include/
	├── lib/
	│   └── python3.11/
	│       └── site-packages/
	└── pyvenv.cfg
	```

### Key Components
1. The `bin/` (or `Scripts/`) Directory
	- Contains the entry points for the interpreter and command-line scripts.
	- `python` / `python3`: Symlinks (or hard copies on some Windows setups) pointing back to the base system Python interpreter that created the environment.
	- `pip`: Executable script bound specifically to install packages into this environment’s local `site-packages`.
	- `activate` scripts: Shell helper scripts designed to modify the current terminal environment variables.
2. The `lib/pythonX.Y/site-packages/` Directory
	- Contains all third-party dependencies installed via `pip` while this environment is active.
	- Standard library modules are not duplicated here; instead, the interpreter resolves standard library imports using the base installation referenced in `pyvenv.cfg`.
3. The Core Driver: `pyvenv.cfg`
	- It is the core configuration file that tells Python it is running inside a virtual environment.
	- When the python binary in `.venv/bin/` is executed, the interpreter looks for `pyvenv.cfg` in its parent directory.

#### How `pyvenv.cfg` Alters Interpreter Behavior:
1. Prefix Redirection:
	- Upon identifying `pyvenv.cfg`, Python sets `sys.prefix` and `sys.exec_prefix` to point to the `.venv` directory instead of the global `/usr` directory.
2. `sys.base_prefix` Preservation:
	- Python retains the path to the underlying system Python installation in `sys.base_prefix`.
3. Site-Packages Isolation:
	- `site.py` reads `include-system-site-packages`.
	- If set to `false`, the global `site-packages` directory is excluded from `sys.path`, isolating project dependencies from global system packages.


## Built-in `venv` vs. Low-Level Virtual Environment Tools (`virtualenv`)
- While `venv` and `virtualenv` accomplish similar end-user goals, their underlying mechanisms and feature sets differ significantly.

| Feature | Standard Library `venv` | Third-Party `virtualenv` |
|---|---|---|
| Availability | Built into Python 3.3+ standard library | Must be installed via `pip` or system package manager |
| Creation Speed | Moderate (copies/symlinks files, slow `pip` seed) | Faster (uses pre-cached wheel bundles for seeding) |
| Arbitrary Python Versions | Can only create environments for the currently running Python version | Can create environments for different installed Python versions using `-p` / `--python` |
| Extensibility | Fixed implementation | Programmable API with support for custom seeders and creators |
| Legacy Python 2 Support | No | Historically supported legacy versions |

### Recommended Usage
- Use `venv` for standard Python application development when relying strictly on Python `stdlib` dependencies without needing extra tools installed.
- Use `virtualenv` when building low-level tooling, operating in CI/CD pipelines where creation speed is critical, or managing environments across multiple distinct installed Python binaries.

## Environment Activation, Deactivation, and Isolation Pitfalls

### What Activation Actually Does (and Doesn't Do)
- A common misconception is that we must run `source .venv/bin/activate` for Python to use a virtual environment.
- In reality, the `activate` shell script performs only two simple operations in the current terminal session.
- Prepends `.venv/bin` to the `$PATH`. This ensures that typing `python` or `pip` in the shell resolves to `.venv/bin/python` or `.venv/bin/pip` first.
- Modifies the shell prompt. Appends `(.venv)` to the terminal prompt string for visual clarity.

### Executing Without Activation
- Because the `.venv/bin/python` executable independently checks for `pyvenv.cfg` in its parent folder, activation is completely optional.
- We can run commands directly using the absolute path to the virtual environment binary.
- This direct invocation pattern is the recommended approach for automated scripts, Docker entrypoints, systemd service units, and CI/CD pipelines.

```bash
# Executing directly without sourcing activate
/home/user/project/.venv/bin/python main.py

# Installing dependencies directly into the virtual environment
/home/user/project/.venv/bin/pip install requests
```

### Deactivation Mechanics
- Running `deactivate` restores the original shell environment by invoking a shell function declared inside the `activate` script.
- Reverts `$PATH` to its pre-activation state.
- Restores the original terminal prompt.
- Unsets the `$VIRTUAL_ENV` environment variable.

### Critical Isolation Pitfalls

#### The Shebang Problem (`#!/usr/bin/env python`)
- If an installed CLI script uses `#!/usr/bin/env python` and is executed outside an activated environment, it will run against the system Python interpreter instead of the project's `.venv` interpreter, leading to `ModuleNotFoundError`.

#### Global Package Leaks
- If `pyvenv.cfg` contains `include-system-site-packages = true`, packages installed in the global system `site-packages` will leak into the environment.
- This creates hidden dependencies that cause builds to break when deployed to clean production servers.
- It is recommended to keep `include-system-site-packages = false`.

#### Broken Symlinks Across System Updates
- Because `venv` creates relative or absolute symlinks back to system binaries (like `/usr/bin/python3.11`), upgrading or removing the underlying system Python installation via a system package manager (`apt`, `brew`) can break virtual environments that rely on those symlinked paths.
