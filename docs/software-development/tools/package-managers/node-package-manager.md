# Node Package Manager

# Introduction
- `npm` is a free library and registry for JavaScript software packages.
- Consists of three distinct components:
    - The website, https://docs.npmjs.com
    - The Command Line Interface (CLI)
    - The registry, a large public database of JavaScript software and the meta-information surrounding it.
## Why use npm?
- Dependency Management
- Large library
- Version Management
- Script Execution
- Publishing
- Community Support
- Integration with Build Tools
- Cross-Platform Compatibility

# Packages and Modules

## Module
- Any file or directory in the node modules directory that can be loaded by the Node.js `require()` function.
- To be loaded by the Node.js `require()` function, a module must be one of the following:
    - A folder with a `package.json` file containing a `”main”` field.
    - A JavaScript file.

## Package
- A file or directory that is described by a `package.json` file.
- A package must contain a `package.json` file in order to be published to the npm registry.
- Since modules are not required to have a `package.json` file, not all modules are packages.
- Only modules that have a `package.json` file are also packages.
- `npm` recommends including a `README` file and it must be in the root-level directory of the package.

## package.json
- Lists the packages the project depends on.
- Specifies versions of a package that the project can use using semantic versioning rules.
- Makes the build reproducible, and therefore easier to share with other developers.
- Packages published to the registry must contain a `package.json` file.
- To make the package easier to find on the npm website, it is recommended to include a custom description in the `package.json` file.
- A `package.json` file must contain
    - `”name”` field that contains the package’s name.
    - `”version”` field must be in the form `x.x.x` and follow the semantic versioning guidelines.

### Problem
- `package.json` does not include nested dependencies.
- As a result, different machines may install different versions of these nested dependencies, which may contain breaking changes.

## npm-shrinkwrap.json
- A file generated by npm that locks down the versions of all dependencies and their transitive dependencies.
- It ensures that the exact same versions are installed across different environments or by different users.
- It contains a flattened and locked version of the dependency tree, including all dependencies and their versions.
- Run npm shrinkwrap to generate or update the `npm-shrinkwrap.json` file based on the currently installed dependencies.

### Problem
-  The order in which the nested dependencies would go when running npm install was unpredictable.
- So, results could be different in different machines.

## package-lock.json
- Similar to `npm-shrinkwrap.json`, this file locks down the versions of all dependencies and their transitive dependencies.
- It is automatically generated by npm and is primarily used for npm’s internal dependency resolution and installation process.
- It contains a detailed dependency tree with specific versions and integrity hashes for each package, ensuring deterministic installs.
- Describes the exact tree that was generated, such that the sub-sequent installs are able to generate identical trees, regardless of immediate dependency updates.
- Optimize installation by skipping repeated metadata resolution for previously installed packages.

### Benefits
- Unlike `npm-shrinkwrap.json`, `package-lock.json` is predictable, and gives same result on all machines.
- Guarantess to install exactly same dependencies accross machines.
- Greater visibility in tree changes through readble source diff.

## Summary
- `package.json` provides metadata and dependency declarations.
- `package-lock.json` is an internal file used by npm for dependency resolution and deterministic installs.
- `npm shrinkwrap` repurposes `package-lock.json` into a publishable `npm-shrinkwrap.json` or simply creates a new one.
- If the package contains `npm-shrinkwrap.json`, npm prioratizes this over p`ackage.json` during `npm install`.
- Unlike `package-lock.json`, `npm-shrinkwrap.json` may be included when publishing a package.
- The recommended use-case for `npm-shrinkwrap.json` is applications deployed through the publishing process on the registry, deploying a CLI tool.

# Dependecies
- Dependencies are specified in a simple object that maps a package name to a version range.
- Dependencies can also be identified with a tarball or git URL.
- To specify the packages a project depends on, developers must list them as "`dependencies`" or "`devDependencies`" in the package’s `package.json` file.
- `dependencies` include the packages required by the application in production.

## `devDependencies`
- Packages that are only needed for local development and testing.
- These dependencies may be needed at some point during the development process, but not during execution.

## `optionalDependencies`
- Packages that are not essential for the functioning of the application but provide additional functionality if they are present.
- If an optional dependency fails to install, npm will continue to install other dependencies.
- Running `npm install --omit=optional` will prevent these dependencies from being installed.

## `peerDependencies`
- Consists of all the packages that are exactly required in the project or to the person who is downloading and the version numbers should also be the same.
- These are not automatically installed. Dev need to manually modify the `package.json` file in order to add a Peer Dependency.
- These are only encountered when dev publish their package.

# CLI Commands

## `npm run-script`
- Aliases: `run`, `rum`, `urn`
- This runs an arbitrary command from a package’s "`scripts`" object.
- If no "`command`" is provided, it will list the available scripts.

## `npx`
- Stands for ”Node Package Runner” or ”Node Package eXecute”.
- Allows running an arbitrary command from an npm package (either one installed locally, or fetched remotely), in a similar context as running it via `npm run`.
- Allows executing a package that isn’t installed on machine. `npx` installs the package temporarily for the duration of the command and removes it once the command is complete.

## Audit
- Audit reports contain tables of information about security vulnerabilities in a project’s dependencies to help developers fix the vulnerability or troubleshoot further.
- Run `npm audit` to audit the packages in a project. If any vulnerabilities are found, then the impact and appropriate remediation will be calculated.
- npm automatically runs this command when running `npm install`.
- The command will exit with a 0 exit code if no vulnerabilities found, and a non-zero code if any vulnerability is found.
- npm version 6 is required for auditing.
- By default npm requires a `package-lock` or `shrinkwrap` in order to run the audit.
- The package lock can be bypassed with `--no-package-lock` but the results may be different with every run, since npm will re-build the dependency tree each time.
- Run `npm audit fix` to automatically install compatible updates to vulnerable dependencies.
- Run `npm audit signatures` to ensure the integrity of packages downloaded from any registry that supports signatures.

### Vulnerability table fields
- **Severity:** The severity of the vulnerability, determined by the impact and exploitability of the vulnerability in its most common use case.
- **Description:** The description of the vulnerability. For example, ”Denial of service”.
- **Package:** The name of the package that contains the vulnerability.
- **Patched in:** The semantic version range that describes which versions contain a fix for the vulnerability.
- **Dependency of:** The module that the package with the vulnerability depends on.
- **Path:** The path to the code that contains the vulnerability.
- **More info:** A link to the security report.

### Provenance statements
- These allow user to publicly establish where a package was built and who published a package. - `npm provenance` includes two types of attestations:
    - **Provenance attestation**, established by publicly providing a link to a package’s source code and build instructions from the build environment. This allows developers to verify where and how a package was built before they download it.
    - **Publish attestation**, generated by the registry when a package is published by an authorized user. When an npm package is published with provenance, it is signed by Sigstore public good servers and logged in a public transparency ledger, where users can view this information.

## `npm ci`
- Clean install a project, similar to `npm install`, except it’s meant to be used in automated environments.
- The project must have an existing `package-lock.json` or `npm-shrinkwrap.json`.
- If dependencies in the package lock do not match those in `package.json`, `npm ci` will exit with an error, instead of updating the package lock.
- `npm ci` can only install entire projects at a time. Individual dependencies cannot be added with this command.
- If a node modules is already present, it will be automatically removed before `npm ci` begins its install.
- It will never write to package.json or any of the package-locks.

# Alternatives
- npm is tightly integrated with the Node.js ecosystem and has been the default package manager for longer, which means some tools and projects might have better support for npm out of the box.

## Yarn
- Created by Facebook, an alternative to npm to address some of the issues developers faced, such as performance, consistency, and security.
- Has faster installation compared to npm due to caching and parallel installation.
- Introduced the `yarn.lock` file, which ensures that the same package versions are installed across different environments. npm later adopted a similar mechanism with `package-lock.json`.
- Introduces additional complexity in configuration, which is a overhead in small projects.

## `pnpm`
- Stands for ”Performant NPM”.
- Creates a single version of each package in a global store and links them to projects using hard links and symlinks. This also helps in faster installation.
- While pnpm is largely compatible with npm, there may be some edge cases where tools or scripts are specifically designed for npm and may not work perfectly with pnpm.
- As pnpm is less widely used than npm, it has a smaller community and fewer resources available.

## `jspm`
- Stands for JavaScript Package Manager.
- Integrates seamlessly with `SystemJS`, a dynamic module loader, enabling it to handle module loading and dependency management effectively.
- It is designed with a focus on ES modules, making it well-suited for modern
- JavaScript development and enabling easier use of the latest language features.
- Allows developers to manage and load JavaScript modules directly in the browser or for use in Node.js environments, without needing a build step, which can simplify development and improve load times during development.
- Integrating it with traditional build tools like Webpack or Babel can be more complex and may require additional configuration.
- The dynamic nature of `SystemJS` can introduce performance overhead during module loading, which might not be ideal for all production environments.
